# 《余烬镇》首版开发方案与工作室评审
版本：0.2 · 2026-10-15

本版纳入用户新增的《八方旅人》视觉参考，以及五个专业 agent 的两轮独立与交叉评审，替代 0.1 中的纯二维路线、首版范围和制作顺序。

当前完成的是资料研究、环境只读检查与设计评审。未安装第三方游戏技能，未开始游戏编码，未运行游戏、导出桌面包或验证画面。本文的时间、数量、规格和性能指标均是拟议目标。

## 1. 游戏方向
做一款自己愿意反复玩的电脑单人游戏：俯视斜角即时动作，像素角色置于真正立体的场景中，配合冷暖灯光、空间遮挡和适度景深。

已明确的乐趣：
- 亲自移动、攻击、闪避、探索和挑战首领。
- 近战、元素法术、召唤可以混搭。
- 永久保留已经获得的装备、经验与已学技能，死亡后继续挑战。
- 稀有掉落有惊喜，毕业武器、套装有明确追求。
- 学会新技能、选择专精、完成觉醒，角色外观随成长变化。
- 在小镇接任务、认识 NPC，逐步开启地下城。

《八方旅人》提供视觉参考；DNF 提供刷装备、角色成长和城镇冒险的体验参考。角色、世界、场景、技能和素材采用原创设计。

## 2. 本轮真实开展的团队工作
主协调者负责制作人职责，另启动五个 agent：

| 岗位 | 本轮工作 | 后续开发职责 |
| --- | --- | --- |
| 制作人／协调者 | 整理用户偏好，组织两轮评审，处理冲突 | 维护范围、版本、依赖和交付结论 |
| 系统策划 | 审查掉落、套装、成长和任务节奏 | 设计数据、关卡与体验目标 |
| 主程／技术负责人 | 比较引擎与渲染路线，查官方文档，检查环境 | 场景、输入、战斗、存档、构建 |
| 美术负责人／技术美术 | 规划像素角色与立体场景融合、动画预算 | 资产规范、灯光、动作、特效和外显成长 |
| QA／独立体验评审 | 提出验收证据和缺陷门槛，反驳无证据通过 | 复现问题、检查规则、截图录像、回归 |
| 技能／工具链工程师 | 核实 skill 原文、依赖、接入状态 | 审核工具、固定版本、支持自动化 |

这是一组 AI 协作岗位，不等于已有真实游戏公司的人力或无限生产能力。AI 能检查规则、画面问题与设计一致性，用户自己的试玩感受仍是乐趣判断依据。

### 第一轮：独立评审
发现四个问题：
1. 原方案把装备、套装、专精、觉醒、打造与地图解锁全部压进 15～20 分钟，难以看清每个系统的收益。
2. 原本准备最后完善美术；新增立体像素风后，镜头、角色比例、受光和遮挡会直接影响战斗，需要前置。
3. 可查到的官方 Game Studio 技能主要面向浏览器，不能据此直接选择 Phaser 作为桌面立体像素项目的引擎。
4. 四向人物挥砍配合任意鼠标方向伤害，可能出现画面与判定不一致。

### 第二轮：交叉质疑与修改
| 争议 | 最终处理 |
| --- | --- |
| 当前没有确认 Godot 运行链，是否先转浏览器制作战斗？ | 维持单一 Godot 主工程；先补运行验证。转 Phaser 会引入场景、物理、渲染和资源迁移，不能称无成本过渡 |
| 四向身体是否能自由瞄准？ | 先验证中性身体姿势＋独立武器连续转向；方向提示、轨迹和命中共用一个向量；失败则整套吸附四向 |
| 首视觉房间能否只做移动与灯光？ | 加入实际攻击、预警、掉落与最小召唤物，检查动作场景下的可读性 |
| 首版是否做所有装备独立换装？ | 外显先做两把武器、一个套装配饰和成长光效；全部防具纸娃娃延期 |
| 是否立即做三条职业线与各自觉醒？ | 一个可重配主修印记；完整觉醒树延期，冒险切片末尾考虑一个可实战释放的共享短觉醒 |
| 觉醒制作超出可行边界怎么办？ | 明确延期觉醒；本轮只验收刷宝与初次成长，不用按钮或演示视频替代已实现技能 |

### 实际接入顺序
1. 先固定项目引擎版本、目录结构和资产约定。
2. 编程以官方文档为准，参考社区 GDScript 规范；仅按需要补读详细模式。
3. 精灵流程先制作合格种子帧，再产出动画条、统一尺度和脚底锚点，进引擎复核。
4. 如试用官方精灵脚本，先审读画布构建、动画归一化、预览输出三个脚本及依赖。
5. gda 先在可丢弃副本验证安装、项目写入、运行控制和导出；特别检查 daemon/harness 对项目的改动。
6. 即使不接入 gda，也可使用 Godot CLI、项目内调试脚本与真实运行截图构建验证流程。

本轮不创建新的个人 skill，也未将候选技能复制进安装目录。

## 4. 推荐技术方案
推荐以 Godot 4 稳定版、GDScript、3D 场景和 AnimatedSprite3D 像素人物作为单一主工程，先选择桌面 Forward+ 渲染档验证。具体版本需在安装阶段固定，不混用引擎与导出模板版本。

这是基于需求与官方能力资料作出的技术建议，不是性能实测结论。Mobile 可在有性能证据后作为同工程优化路径评估。

Godot 的 SpriteBase3D 支持把二维纹理放入三维空间；人物受光和透明方式需要显式设置。内置景深支持 Forward+ / Mobile，Compatibility 不支持。因此网页预览不能替代桌面画面验收。

### 空间、镜头与动作
- 首版固定斜角镜头；在实际房间比较正交与窄视角透视，再锁定镜头。
- 先使用一个 XZ 战斗平面，石阶作为装饰，不引入跨高度攻击规则。
- 鼠标投射到地面得到攻击方向；提示、武器轨迹、法术和命中共享方向。
- WASD 按相机地面方向映射；碰撞体、脚底和掉落都对齐地面。
- 首测四朝向身体、八方向移动，独立武器承担连续瞄准表现；不称作八方向完整动画。
- 重点检查 22.5°、45°、67.5° 与身体朝向切换边界。
- 若武器离手、像素旋转抖动或朝向跳变不能接受，则提示、动画与判定一起吸附四向，后续再投入八向动作。
- 战斗地面、敌人前摇、危险范围、掉落与召唤物保持清楚。景深主要服务非战斗前远景。

### 数据与交付
装备、技能、任务、奖励采用稳定 ID。存档版本化，使用临时文件替换并保留有效备份。奖励结算不依赖房间是否重新生成。

建议首交付为 Windows x86_64 桌面包。系统和显卡待确认；不继承用户其他项目的 Windows 7 兼容要求。导出成功与目标电脑实际启动分别验收。

### 环境检查所得
主程已做只读检查：Node、npm、Python 可用，Playwright 模块可解析；PATH 未发现 Godot，默认 Playwright 浏览器执行文件未发现，当前也没有已验证的本地图形渲染、导出模板或 Windows 启动证据。

这些检查只描述当前已检查范围，不能证明平台不存在其他图形能力。当前不能报告“样机已运行”“桌面包可用”或“达到某帧率”。

## 5. 美术生产与验收
视觉目标：像素角色、立体矿井、暖火光、冷环境光、清楚的前后遮挡和适量后期。像素纹理密度与人物尺度统一，中文 UI 保持清楚。

首样板约包含：
- 一个固定镜头矿井房间，约十个可复用场景模块。
- 一个四朝向主角、一个敌人、一个最小召唤物。
- 两个独立武器外观、宝箱、入口和火把。
- 斩击、命中、元素法术、召唤和稀有掉落效果。
- 血条、技能栏、拾取提示和装备比较。

人物建议先用约 64×64 的透明单帧画布起测，具体像素比例须在镜头里验证。帧数是生产预算，不是通过率；精简主角也可能需要数十帧，补全角色、敌人与首领后会达到数百帧量级。

资源生产顺序：
1. 角色造型 → 同尺度方向姿势 → 最少移动与持握 → 引擎尺度验证 → 补动作与武器挂点。
2. 敌人攻击规则 → 可辨认剪影 → 前摇与攻击动画 → 实际伤害帧对齐。
3. 场景色稿 → 3D 模块白盒 → 像素纹理 → 遮挡规则 → 灯光 → 最后调后期。
4. 合格源资源 → 图集、标签与时长 → 运行预览 → 缺陷修正。

单张概念图只用于判断审美。动画连续性、方向一致、透明边缘、脚底锚点、武器持握、碰撞、灯光、遮挡和帧率，都需要另外验证。

## 6. 三阶段制作范围
| 阶段 | 内容 | 可供决策的结果 |
| --- | --- | --- |
| A：可运行视觉样板 | 一个房间、角色、敌人、最小召唤物、近战与法术、两把武器、灯光与遮挡 | 实际截图和运动录像，能判断画风与即时动作是否协调 |
| B：战斗与掉落样机 | 两种敌人、普攻与闪避、法术召唤混搭、两种装备组合、保底机制装备 | 可以亲手完成战斗、捡装备和换装，理解打法变化 |
| C：两趟冒险切片 | 小镇一角、两个交互 NPC、最多四个战斗房和一个首领房、短支路、套装与存档 | 接任务到回城成长完整可玩，并有自愿再次挑战的机会 |

阶段 C 首次体验目标约 25～35 分钟，以实测为准。首版以四个装备位、八至十件装备为建议预算。装备位先采用武器、衣装、护符、戒指；三件套覆盖后三位，独立武器与非套装替代品须有实际选择价值。

延期：完整十级成长曲线、强化继承、分解、随机词缀、多职业、完整纸娃娃、随机地图、多流派觉醒树和大型城镇。基础经验与等级可在后续增加；保留成长的玩家承诺适用于实际已实现的成长系统。

阶段 C 末尾可加入一个通用短觉醒，复用基础身体动作，通过独特武器与地面特效提供可操作的成长节点；若延期，必须在交付清单中说明。

## 7. 让装备追求成立
- 首杀保底一件可立即使用、改变行为的机制装备，便于体验首次成长。
- 后续有随机掉落，同时显示专属武器和套装的材料兑换进度。
- 套装两件有用、三件改变打法；非套装组合也能完成首领挑战。
- 第一轮组合示例：近战＋冰霜的控制与碎冰；近战＋召唤的标记与集中攻击。
- 关键武器、套装配饰和技能效果先承担“变帅”，不让所有装备都产生独立身体素材需求。

首杀后允许直接结束试玩，同时展示未获得的装备目标。观察用户是否主动查看目标、调整搭配、再次进图；不用强制后续任务替代自主追求。单个用户的行为和原话作为反馈，不报告虚构留存率。

## 8. 迭代流程与岗位责任
每轮采用：策划列目标 → 主程与美术评估依赖 → 分模块制作 → 集成版本 → QA 复现与证据 → 修复 → 回归 → 制作人汇总 → 达到门槛后交用户体验。

执行约定：
- 同一文件设负责人，避免多个 agent 同时改写。
- 装备 ID、技能事件、资产锚点、动画标签和存档结构先约定。
- 每轮保留版本、变更、运行步骤、缺陷和已知限制。
- 把已读资料、已写代码、已运行测试、已导出、已在用户设备启动分别记录。
- 用户决定视觉感受、乐趣和扩展优先级；团队负责提出并验证技术实现。
- 不预先承诺固定轮数就达到参考作品品质；以门槛和实际反馈推进。

未来进入开发后，可拆分战斗、成长存档、场景、美术与测试任务；当前不为了岗位数量创建彼此依赖的大量空工程。

## 9. QA 门槛与证据
| 门槛 | 必查内容 | 留存证据 |
| --- | --- | --- |
| G0：运行能力 | 固定引擎能导入并真正渲染 | 版本、导入状态、实际截图；headless 检查单独列出 |
| G1：画面与动作 | 走位、像素锚点、受光、遮挡、攻击轨迹、危险提示、三类战斗同屏 | 无后处理/完整效果、墙前后、不同攻击角度、换武器的运行录像 |
| G2：装备与构筑 | 套装生效、两种组合不同、方向提示与命中一致 | 固定测试构筑、规则检查和运行对照 |
| G3：存档与奖励 | 死亡保留成长、重开保留、任务与奖励不重复 | 存档前后状态、复现步骤、界面对照 |
| G4：桌面包 | 目标 Windows 启动、输入、缩放、中文路径、流畅度 | 导出日志与目标机测试分开，记录 GPU/分辨率/画质/帧时间 |
| G5：乐趣 | 能理解装备变化，愿意自主决定是否再刷 | 具体操作、原因与原话 |

崩溃、丢档、流程卡死需要修复；关键战斗不可读、装备无效果、奖励重复结算也不能当作正常交付。轻微美术问题可以带明确已知问题交试玩。

AI 无法替代用户最终判断是否喜欢。静态图、规则通过、导出成功、目标机启动和真正玩得开心是不同证据，不能互相替代。

## 10. 给用户的决策顺序
推荐直接进入阶段 A 的运行验证准备，无需用户先挑引擎或逐个挑 skill。

第一项体验决策：看过真正运行的像素角色＋立体房间后，确认是否符合期待，再批量制作地图和动作。

第二项体验决策：玩过完整冒险切片后，决定优先扩装备构筑，还是扩城镇任务与地图。

可以提前收集目标电脑系统、显卡型号和常用分辨率；这些用于画质与性能档，不阻碍本轮设计结论。
